Held Apart for Watching

It reads Python code. It looks for calls that write a value into a log. It reports the calls where the logged message is built directly from a named value, with no cleaning step in between. Unsanitised input written straight to a log lets an attacker place false entries in that log. The tool looks for the code shape that allows this. It does not run the code. It does not watch a live log. It reads a file and reports line numbers.

Calls This Scan Can See

The file is parsed into a syntax tree. The scan walks that tree. It is not a line by line text search. A call counts as a log call only when two facts hold. The receiver is the name logging or the name logger. The method is one of info, error, warning, debug, or critical.

A Logger Under Another Name Is Not Seen

Only two receiver names are seen. A logger held under a different name is not seen. A logger reached through self.logger is not seen. A log call of exactly the risky shape is missed in both cases. A clean result means no risky call was found among the calls this scan can see. It does not mean the file has no log calls.

Shapes That Are Reported, and the Lazy Form Is Left Alone

The first argument is then tested. A bare name is reported. An f-string that holds a name is reported. A value built by percent formatting or by addition, where the build holds a name, is reported. A format call that holds a name in its arguments is reported. One form is not reported: a call that passes a constant format string first and the value as a later argument is the lazy form, and the code leaves it alone.

Scope and limits, and Findings by File and Line

A directory scan reads only files that end in .py. A single file given directly is attempted whatever its ending is. A file that is not Python will fail to parse and is then counted as not scanned. Each finding is reported as one line giving the file, the line number, and the text of the line, and the same line is written as a warning in the log output.

Results Are Appended, Never Cleared

If an output file is named, findings are appended to it. The file is opened in append mode for each finding. It is never cleared first. A second run at the same path adds its findings below the first run findings. A file that cannot be read, decoded, or parsed is listed as not scanned, and its name is also appended to the output file where one is named.

Not Scanned Is Not Clean, exits

A run with findings exits 1. A run with a failed file exits 1. A run with neither finishes without an exit call and ends at 0. A path that does not exist is refused and exits 1.

# codeintel-Log-Injection-Analyzer

Scans code for potential log injection vulnerabilities by identifying unsanitized user input that is directly written to log files, allowing attackers to inject malicious log entries. - Focused on Tools for static code analysis, vulnerability scanning, and code quality assurance

## Install

`git clone https://github.com/ShadowGuardAI/codeintel-log-injection-analyzer`

## Usage

`./codeintel-log-injection-analyzer [params]`

## Parameters

- `-h`: Show help message and exit

- `-l`: No description provided

- `-o`: Path to the output file for results.
